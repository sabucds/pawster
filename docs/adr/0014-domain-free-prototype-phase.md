# The prototype phase runs without a domain, and email is what that costs

[ADR 0011](0011-r2-custom-domain-requires-a-full-zone.md) concluded that a domain bought fresh for Pawster costs nothing to delegate, and treated the registration itself as the one permitted expense. That expense is now declined: the project is to be built with no domain at all, on hostnames the free tiers generate. This ADR records what that buys, what it forecloses, and the single condition that ends the phase.

The requirement can be read as three separate needs, and they do not fail together.

**The app needs no domain.** ADR 0007's governing mechanism is Astro's Static Assets, which Cloudflare serves *"without invoking Worker code"*, free and unlimited, and outside the 100,000 requests/day cap. All of that is true of a `workers.dev` deployment. The prerendered listing, the browser-side filtering of the JSON index, the islands and the i18n are unaffected. Nothing in ADR 0007 is compromised by the absence of a domain.

**Images need no domain, at this scale.** R2's auto-generated `pub-<hash>.r2.dev` hostname serves public objects with no zone. ADR 0011 rejected it because it is not CDN-cached, which makes every image view a billable Class B `GetObject` rather than an edge hit. That reasoning is sound and still stands — but `docs/research/free-tier-image-storage.md` computes the consequence, and the consequence is small for now: 10M Class B operations per month against ~28 image requests for a lean session is **~357,000 sessions/month**, and that figure *already assumes zero cache hits*, which is exactly the `r2.dev` condition. `r2.dev` costs the growth phase, not the prototype. Its live risks here are the variable, unpublished rate limit and Cloudflare's statement that the hostname is *"not intended for production usage"* — both real, neither billing-related.

Transformations are a non-issue, because ADR 0007 already pre-generates every derivative at upload time, so the documented refusal of transformations on Cloudflare-provided dev subdomains never applies.

**Email needs a domain, and there is no substitute.** Resend verification requires an MX record, an SPF `TXT` and a DKIM `TXT` published *at the sending domain*. A free-tier hostname — `workers.dev`, `pages.dev`, or any equivalent elsewhere — exposes no DNS, because the zone belongs to the platform. This is not a gap in Cloudflare's or Resend's free tier that a different vendor closes: `docs/research/free-tier-email-sending.md` surveyed the field, and every provider that can reach a public list requires a verified domain. Resend's sandbox reaches only the account's own address; Mailgun's free tier reaches about five individually-activated recipients; SES sandboxes new accounts to verified recipients pending manual review; Postmark requires approval and your own verified domains; SendGrid retired its free tier outright.

So the decision is: **build the whole product on generated hostnames, and accept that Pawster can send email only to its operator.**

## Consequences

- **The public product is fully real; the private one is single-tenant.** Adopters browse and filter with no email in the path, so the listing ships honestly. But ADR 0013 opens by observing that every actor here "is already authenticated by control of an inbox" — so shelter sign-in codes, the admin verification links of [ADR 0002](0002-no-admin-accounts.md), the confirmation capabilities of [ADR 0008](0008-confirmation-is-a-capability-not-a-session.md) and the digest of [ADR 0009](0009-digest-delivery-and-retry.md) all work for one inbox only. During this phase the operator is the only shelter.
- **Every email path is still built and testable.** The sandbox delivers to the operator's real inbox, so sign-in, confirmation, retry and digest composition are exercised end to end against a real provider. What is deferred is the recipient list, not the code.
- **The phase ends on a person, not a date.** Onboarding a second shelter, or accepting one real subscriber, requires a domain that day. There is no partial version of this: the first non-operator human who needs an email ends the phase.
- **Reversal is a config change plus a DNS wait.** `R2_PUBLIC_HOST` is an environment value, not a hardcoded host, so adopting a domain later means attaching a custom domain, verifying the Resend subdomain, and changing one variable. Nothing about this phase has to be unbuilt.
- **ADR 0011 is suspended, not overturned.** Its reasoning about full zones and the Business-plan gate on partial setups is untouched, and it governs again the moment a domain exists. This ADR narrows its scope to "once there is a domain" rather than contradicting it.
- **The $0 posture is now load-bearing in a place it was not.** ADR 0006 accepted a grey zone in Cloudflare's "Paid Services" clause; serving production images from a hostname documented as not intended for production widens it slightly. Recorded here so a future session reads it as a known position rather than an oversight.
- **`--no-domain` is the mode that implements this**, and it refuses to overstate itself: it labels the provisioning record as *partially* addressing [#18](https://github.com/sabucds/pawster/issues/18), lists the four skipped stages, and declines to advise closing the ticket.

## What was rejected

- **A free `.eu.org` domain**, which would have preserved ADR 0011 intact — it is on the Public Suffix List, so Cloudflare treats it as a normal registrable apex and a full zone works. Rejected because none was available to this project. Worth re-reading before paying for a domain, since it is the one option that costs nothing and concedes nothing.
- **Serving images through a Worker to obtain caching.** A Worker can read R2 through a binding and use the Cache API without any custom domain, but every image request would then consume one of the 100,000 daily Worker invocations that ADR 0007 exists to protect — trading a meter with a 10M/month allowance for one with 100k/day. `r2.dev` is the cheaper uncached option.
- **Sending as a free-webmail address through a third-party ESP.** It fails DMARC alignment for a domain we do not control, which is the exact pattern spam filtering is built to catch, and providers increasingly refuse it. It would produce mail that is sent but not delivered — worse than not sending, because the failure is invisible.
