# Prerender first, and filter in the browser over a static index

Pawster is an Astro site on Cloudflare Workers, and its governing rule is that **the Worker should run as rarely as possible**. Cloudflare's own limits page puts server-side rendering at 10–20 ms of CPU against a 10 ms Free-plan ceiling, while a file served from Static Assets is served "without invoking Worker code", is free and unlimited, and does not count against the 100,000 requests/day cap. So rendering strategy is not a preference here; it is what keeps the site inside the free tier at all.

Astro was chosen over the alternatives because its default posture already is this: everything is static, and a route opts into server rendering with `export const prerender = false`. Its islands architecture ships no JavaScript unless a component asks for it, which is the metered-Venezuelan-connection constraint handled by the framework instead of by discipline. And its i18n is the only built-in one among the candidates — `defaultLocale: "es"` with `prefixDefaultLocale: false` gives unprefixed es-VE at the root and prefixed English as configuration rather than middleware we would own and test. Next.js was ruled out on a hard number: OpenNext's own documented example bundle is 2,295.89 KiB gzipped against the Free plan's 3 MB Worker limit, leaving almost no room for our code, and Cloudflare has since demoted OpenNext in favour of a beta.

That leaves the real problem: the listing is filterable across six axes, and prerendering every permutation is combinatorial. **We generate a compact filter index as a JSON file in R2 and filter it in the browser.** Publishing an animal writes a fresh index; reads hit R2 through the custom domain, so they cost no Worker invocation, no CPU and no egress, and every filter interaction after the first load costs no request at all.

## Consequences

- The only server-rendered routes are the shelter publishing area, the signed-link pages, and the animal detail page — one row from D1, comfortably inside 10 ms. Everything an anonymous adopter browses is static.
- **The filter index carries only what a filter or a card needs**: id, name, species, region, size, sex, good-with flags, thumbnail key, plus `estimatedBirthDate` and `lastConfirmedAt`. Free-text descriptions and full photo sets stay on the detail page. When the index stops being cheap to download on a metered connection, filtering has to move server-side — that, not animal count, is the trigger.
- **The index must carry the two dates, never the derived bands.** An earlier version of this ADR listed "age band" among the index fields, which is wrong: the index is written at publish time, so storing the *band* freezes it. A dog crossing from `Puppy` into `Young` would re-band only when someone happened to republish it, reintroducing exactly the invisible scheduled writer [ADR 0004](0004-age-bands-are-derived.md) exists to avoid — and the same argument applies to staleness under [ADR 0001](0001-no-automatic-unlisting.md). The index carries `estimatedBirthDate` and `lastConfirmedAt`; the browser derives both. Caught by the issue #17 prototype, which derives them in real code rather than seeding band strings.
- **The index is not the page-weight budget this ADR expected; photos are.** This ADR called the index "the thing to watch". Measured at 2,500 animals with real gzip (issue #17): the filter axes alone are 21.6 KB, everything the card additionally needs brings it to **33.4 KB**, and even inlining shelter names and urgency notes as text reaches only 38.6 KB — against a ~150 KB budget for a metered connection. The card's field budget is therefore a **legibility decision, not a payload one**. What does bind is photo payload, which spans **8.6×** across card shapes (83 KB to 717 KB for the same twelve cards) purely on derivative dimensions. Watch the derivative sizes, not the index.
- Publish-to-visible latency is seconds, not a rebuild. The rejected alternative was a full site rebuild on a deploy hook: more conventional, but minutes of latency and it burns build minutes.
- Deriving staleness for display (ADR 0001) stays build-time or client-side work, and never touches the CPU ceiling.
- Two Workers, not one: `web/` (Astro) and `digest/` (a `scheduled` producer and a `queue` consumer), sharing a `db/` package that owns the Drizzle schema and migrations. They bind the same D1 database. Splitting them gives each its own 3 MB bundle and 10 ms CPU budget, independent deploys, and — the reason that matters — lets the digest engine be tested without booting Astro.
- Drizzle with `drizzle-kit` is the access layer. Cloudflare's own migrations documentation names Drizzle and documents the `migrations_pattern` glob for its layout, so `drizzle-kit generate` and `wrangler d1 migrations apply` interoperate. The client is constructed **inside the request handler**, never at module scope: the 1-second startup limit is a deploy-time rejection, and a module-scope client also triggers "Cannot perform I/O on behalf of a different request". *(Amended by [#47](https://github.com/sabucds/pawster/issues/47): the rule stands, the second reason is not observable locally and so cannot be relied on to catch anyone. Measured on 2026-09-03 against `@cloudflare/vitest-plugin@1.1.4`, neither a client built at module scope nor one cached across requests produces that error — both return 200, every time. The 1-second startup limit cannot be seen either, being a deploy-time rejection. The rule is therefore enforced structurally, by `scripts/check-source-rules.mjs`, and the runtime's silence is characterised in `db/test/module-scope-is-wrong.test.ts` so it stays visible. See [`docs/testing-seams.md`](../testing-seams.md).)*
- An SSR route may issue at most 50 D1 queries, because D1 queries are subrequests and share the per-invocation budget.
- Two numbers are unverifiable from documentation and must be measured rather than assumed: the actual gzipped Worker size (`wrangler deploy --outdir bundled/ --dry-run`) and actual per-request CPU on the SSR routes. *(Both are now measured by one command each — `npm run check:bundle-size` and `npm run check:ssr-cpu` — and recorded in [`docs/measurements.md`](../measurements.md): 173.40 KiB gzipped for `web/` and 35.58 KiB for `digest/` against the 3 MB limit, and ~0.7 ms of render CPU against the 10 ms ceiling. They are checks, not tests: **no test in this suite can catch a CPU regression**, because neither the Vitest plugin nor local `workerd` meters CPU or fails an over-budget invocation.)*
