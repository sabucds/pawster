# Prerender first, and filter in the browser over a static index

Pawster is an Astro site on Cloudflare Workers, and its governing rule is that **the Worker should run as rarely as possible**. Cloudflare's own limits page puts server-side rendering at 10–20 ms of CPU against a 10 ms Free-plan ceiling, while a file served from Static Assets is served "without invoking Worker code", is free and unlimited, and does not count against the 100,000 requests/day cap. So rendering strategy is not a preference here; it is what keeps the site inside the free tier at all.

Astro was chosen over the alternatives because its default posture already is this: everything is static, and a route opts into server rendering with `export const prerender = false`. Its islands architecture ships no JavaScript unless a component asks for it, which is the metered-Venezuelan-connection constraint handled by the framework instead of by discipline. And its i18n is the only built-in one among the candidates — `defaultLocale: "es"` with `prefixDefaultLocale: false` gives unprefixed es-VE at the root and prefixed English as configuration rather than middleware we would own and test. Next.js was ruled out on a hard number: OpenNext's own documented example bundle is 2,295.89 KiB gzipped against the Free plan's 3 MB Worker limit, leaving almost no room for our code, and Cloudflare has since demoted OpenNext in favour of a beta.

That leaves the real problem: the listing is filterable across six axes, and prerendering every permutation is combinatorial. **We generate a compact filter index as a JSON file in R2 and filter it in the browser.** Publishing an animal writes a fresh index; reads hit R2 through the custom domain, so they cost no Worker invocation, no CPU and no egress, and every filter interaction after the first load costs no request at all.

## Consequences

- The only server-rendered routes are the shelter publishing area, the signed-link pages, and the animal detail page — one row from D1, comfortably inside 10 ms. Everything an anonymous adopter browses is static.
- **The filter index is a page-weight budget, and it is the thing to watch.** It carries only what a filter or a card needs: id, name, species, region, size, age band, sex, good-with flags, thumbnail key. Free-text descriptions and full photo sets stay on the detail page. When the index stops being cheap to download on a metered connection, filtering has to move server-side — that, not animal count, is the trigger.
- Publish-to-visible latency is seconds, not a rebuild. The rejected alternative was a full site rebuild on a deploy hook: more conventional, but minutes of latency and it burns build minutes.
- Deriving staleness for display (ADR 0001) stays build-time or client-side work, and never touches the CPU ceiling.
- Two Workers, not one: `web/` (Astro) and `digest/` (a `scheduled` producer and a `queue` consumer), sharing a `db/` package that owns the Drizzle schema and migrations. They bind the same D1 database. Splitting them gives each its own 3 MB bundle and 10 ms CPU budget, independent deploys, and — the reason that matters — lets the digest engine be tested without booting Astro.
- Drizzle with `drizzle-kit` is the access layer. Cloudflare's own migrations documentation names Drizzle and documents the `migrations_pattern` glob for its layout, so `drizzle-kit generate` and `wrangler d1 migrations apply` interoperate. The client is constructed **inside the request handler**, never at module scope: the 1-second startup limit is a deploy-time rejection, and a module-scope client also triggers "Cannot perform I/O on behalf of a different request".
- An SSR route may issue at most 50 D1 queries, because D1 queries are subrequests and share the per-invocation budget.
- Two numbers are unverifiable from documentation and must be measured rather than assumed: the actual gzipped Worker size (`wrangler deploy --outdir bundled/ --dry-run`) and actual per-request CPU on the SSR routes.
